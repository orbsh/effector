# 0001 — Containment is declared by the node, and every declaration names its enforcement

> **Languages:** [English](0001-sandbox-declaration.md) (primary) · [中文](0001-sandbox-declaration.zh-CN.md)

**Status:** Accepted (2026-10-14). Landed with this record: the declaration
surface is completed for what the jail can enforce, and unenforceable claims are
refused at startup. Still open: the proxy path for egress allowlists, the
seccomp profile, and a mechanism (or the retirement) of `command_exec`.
**Date:** 2026-10-14

## Context

The effector is the ONLY containment layer for delivered code: the code runs in
a session process, and the jail (bubblewrap, generated by `sandbox-runtime`) is
that boundary — there is no per-operation container beneath it. What the node
promises about that boundary is its `CapabilitySurface`, published to the
control plane in the registration frame.

Audited on 2026-10-14, the declarations and the enforcement did not line up:

- `fs_scope` reached the jail as `allow_write` — enforced — but the field's own
  doc said "paths delivered scripts may read/write". Reads are NOT confined by
  it: everything the jail does not bind read-only is readable. The claim was
  wider than the mechanism.
- `deny_read`, `cwd` and `allowed_domains` existed in `SandboxPolicy` with no
  declaration feeding them — `sandbox_policy_for` hardcoded `deny_read: []`,
  `cwd: temp_dir`, `allowed_domains: []`. The policy structure described a
  surface nobody could state.
- `network` (`none` / `allow` / `open`) and `command_exec` were declared,
  published at registration, and consumed by NOTHING: egress allowlists would
  have to ride `sandbox-runtime`'s proxy (never configured), the jail denies
  egress outright, and no policy field blocks or grants exec inside the jail.
  Two published capabilities that were not capabilities.

So the gap was not "a missing declaration face" — it was declarations with no
enforcement point, which is the lying kind: the control plane routes work by
what a node claims, and a claim the node cannot honor misroutes work onto a
machine that will behave differently than advertised.

## Decision

**RULING — the node's own declaration is the jail's only source, and an
unenforceable claim is a startup error.**

1. **Every jail field comes from the node's `CapabilitySurface`.** Nothing in
   the policy is derived from a control-plane frame, and no field stays
   hardcoded while a declaration for it exists: `deny_read` ← the declared
   `deny_read`, `cwd` ← the declared `cwd` (undeclared = the pre-declaration
   default, the system temp dir), `allowed_domains` ← the declared `network`.
   The source of truth for a machine's jail is the machine.
2. **`fs_scope` is the WRITE scope, and it says so.** Everything outside it is
   read-only, and reads are governed by `deny_read` (credentials, shell
   configs, other users' trees). A field whose documentation overstates its
   mechanism is a documentation bug with security consequences, not a feature.
3. **A declaration with no enforcement point is refused at startup.**
   `EffectorConfig::validate()` runs before the node dials (the same shape as
   the missing-credential failure): `command_exec: true` and any `network`
   other than `none` are errors today, because nothing wires them. The message
   names the missing enforcement point, so the operator learns what to build —
   not just that a value was rejected.
4. **What is not enforceable is named, never hidden.** A field may be declared
   only once its enforcement point exists; until then it is absent from the
   surface (not silently ignored, not "accepted with a warning"), and the gap
   is listed in `docs/PLAN.md` (Phase 5's sandbox bullet) rather than left to be
   rediscovered.

## Considered and rejected

- **Declaring the containment policy on the control plane** (per mount, in the
  prism manifest). The control plane would dictate a machine's jail from
  outside, and mount-level granularity would put policy on the wire for every
  call. The machine is the party that knows what it can expose, and it is the
  party whose misbehavior the claim describes; the offender and the owner are
  the same.
- **Leaving the unenforced declarations in place with a startup warning.** A
  published capability is a promise the control plane routes by; a warning
  nobody reads changes nothing about the promise it keeps making.
- **Enforcing `fs_scope` as a read scope too** (confine reads to the listed
  paths). It would break the ordinary case — a script reading `/usr`, system
  libraries, `/etc` for its runtime — while pretending to be least privilege.
  The deliberate shape is write-confined, read-open, with `deny_read` as the
  read-side declaration.
- **Per-language interception** (python audit hooks, no steel grants, a nu
  pre-parse screen). Rejected earlier and still: one process boundary, not N
  language-specific half-jails that each leak differently.

## Consequences

- `CapabilitySurface` gains `deny_read` and `cwd`; `fs_scope`'s doc is corrected
  to the write scope. Both new fields default to today's behavior, so an
  existing node that declares nothing keeps the jail it had.
- `EffectorConfig::validate()` is called by `remote::run` — the single entry, so
  the binary and every in-process embedder (prism's tests included) get the same
  refusal.
- Tests: the config refusals (`effector-config`) and the declaration→policy
  mapping (`effector-runtime::remote`), both unit-level, next to the code they
  pin.
- `docs/USAGE.md` / `USAGE.zh-CN.md` document the two new fields and the
  fail-closed rule.
- **Still open** (named in `docs/PLAN.md`): the proxy path that would make
  `NetworkPolicy::Allow` enforceable, the seccomp profile, the mechanism that
  could enforce a `command_exec` grant (or that field's retirement), and the
  finer form of read denial (the sandbox runtime accepts patterns, this
  declaration passes strings).
