# 0003 — The environment is the boundary; the capability surface names intent, not safety

> **Languages:** [English](0003-environment-model.md) (primary) · [中文](0003-environment-model.zh-CN.md)

**Status:** Accepted (2026-11-16). Supersedes two records: PLAN Phase 0's "isolation is per-node, the capability surface is the restricted world", and PLAN Phase 5's "the capability surface is the ONLY containment layer — no per-operation container beneath it".
**Date:** 2026-11-16

## Context

ADR-0001 built the containment story around a per-call jail: bubblewrap wrapping one child process, with every declared capability mapped to a field of that jail (`fs_scope` → the write scope, `deny_read` → read denials, `cwd`, `network` → proxy allowlist). The stated reason for the per-call shape was that a container was too slow, and the stated consequence was that the capability surface IS the security boundary: delivered code shares the node's user, its filesystem view, and its process tree, so every operation the model might take had to be named in advance and checked at execution.

Both halves of that reasoning have changed.

**The cost argument is gone.** Measured on this machine against a warm local image: `docker run --rm <image> true` in 0.18–0.21 s, the same with `python3 -c pass` in 0.16–0.23 s, and two interpreter starts inside one container also 0.17 s. The interpreter is inside the noise; the price is container creation. The 2.5 ms figure a container runtime advertises is not the number that matters here — the number that matters is that a per-call container costs about as much as a process spawn did, and a task-scoped container with idle retention costs it once per task instead of once per call. What was slow was a desktop VM and a cold image pull, not the API.

**The security argument was wrong, and the failure is human, not technical.** Per-operation approval is limited by attention, and attention does not scale: a person reading forty permission requests in a row stops reading them, and an automated flow that blocks on an approval it cannot get is worse than one that fails. An audit-based model then has to ask permission for things that are cheap to undo — regenerating a build artifact, deleting a temporary tree — which is absurd on its face and, worse, trains the reader to approve without looking. This is directly opposed to why gravity and aura exist: a system built to run many turns in parallel cannot route its concurrency through a single human's approval queue.

**What actually scales is binding a resource to an environment, not an operation to a permission.** A repository you can read is a resource you may then use however you like, because the damage is bounded by what else you can reach and is undone by `git`. Two persistence mechanisms cover the durable part: **git carries text and code** (versions, rollback, merge) and **object storage carries declared artifacts** (a trained model, a dataset, build output). Inside a container, `rm -rf /` costs the current task and nothing else, and the recovery is to run the task again. That is the model this record adopts, and it retires the capability surface as a security boundary: what a node declares is now what it *intends* to do and what can be audited, not what stands between untrusted code and the host.

## Decision

**RULING — the execution environment is the boundary, and the boundary is chosen per task.**

1. **`Environment` replaces `SandboxPolicy`, and the choice has two axes: who the code belongs to, and what runs it.** The first axis is a trust domain and it decides the safety story; the second is a backend and it decides availability.
   - **In-process** — the code belongs to the engine's own domain: aura's realm scripts, resident per booth (realm Phase 2.6), and the operations aura performs itself. Backend: a call in the node's own address space (`steel`, `python`). No boundary is claimed, because there is nothing untrusted to bound — and that is the honest statement, not a loophole.
   - **Host** — the code belongs to the machine's owner and needs what only the machine has (compose a system config, read a named file). Backend: a child process on the host, no jail; a small grant plus an audit trail instead of an interceptor.
   - **Disposable** — the code belongs to nobody: it was written a moment ago by a model inside a turn. Backend on this host: a container through the Docker Engine API (`Container { image, network, task }`), where nothing of the host is visible, the limits are the container's, and the kill handle is the container. Backend in a cluster, later: a Kubernetes `Job` created through the API — **not** `docker run` inside a pod, since a pod has no daemon.
   The axes are independent on purpose: a machine without Docker loses the disposable class's local backend and keeps the other two, and a cluster gains the disposable class back without changing what the call looks like. What no backend may do is move a call's trust domain: that is declared by the control plane for the code's origin, so a turn's freshly written row cannot be run in-process because in-process happens to be faster.
2. **The contract is three things, and it does not mention processes.** An environment yields an executor: an entry point, a carrier for the induction frames, and a handle that kills it. For a process or container backend the carrier is a pair of pipes; for the in-process backend the frames are values — which is why the contract is stated at the executor, not at the pipe. "Behaves like a child process" was never a requirement; it was how the jail happened to work.

   The retention stories are the same idea in three time frames, and that is not a coincidence: the realm keeps its resident executors for as long as the booth lives (they die with it), a host node keeps nothing between calls, and a container lives through its task's grace period. An environment is retained for its scope, and the scope's end is what ends it.
3. **Containers are keyed by TASK, and the key comes from the control plane.** `ToolCall` carries no task identity today (`call_id`, `kind`, `stream`, `executor`, `entry`, `language`, `encoding`, `args`, `code`), and `memory_scope` inside `CodeRef` is the wrong stand-in: it is the memory surface, it outlives tasks, and two users on one node would collide in it. A missing `task` means a fresh container per call — the safe default, not a fallback that guesses.
4. **Not keyed by environment spec.** Two tasks that happen to want the same image and the same resource set are still two tasks; sharing a container because their spec hashes match would let one user's leftovers be visible to another, and that is a security hole that looks like a cache hit. Same-user sharing would be safe but useless at the scale that needs it: broad parallelism is a cluster's job, and a container on another host or in the cluster cannot be shared anyway.
5. **Not keyed by resource set.** A task discovers what it needs while it runs. A key derived from the resources would force a decision either to restart the container when a resource appears, or to keep the task's declarations frozen at start — both wrong.
6. **Lifecycle is an idle-retention pool, and it saves nothing on the way out.** When a call returns, the container is kept for 15 s. A new call for the same task cancels the timer, runs, and re-arms with double the previous grace (30, 60, 120, 240, capped at 300 s); the cap exists because after minutes of idleness the wait costs more than a cold start, and a task that has been idle that long is not latency-sensitive. On expiry the container is destroyed immediately — no drain, no flush — because durable state was already handled at task completion. A later call for the same task initializes a new container; the image and its dependencies are already on the node, so that costs the same ~0.2 s.
7. **The resource contract is how durable data crosses the boundary, and it exists because credentials cannot.** A resource is `{ name, type, source, ref?, mode }`. `name` fixes the path (`/work/resources/<name>`); `type` names the TRANSPORT, not the content (`git`, `object`, `prefix`, `url`, `snapshot` — a trained model is an `object`; a dataset is usually a `prefix`); `mode` is `ro` or `rw`. Two verbs: `ensure` is idempotent (present → no-op, absent → fetch) and is therefore also the answer to a resource discovered mid-task, which costs a directory appearing, not a restart; `sync` uploads the `rw` resources whose outputs were declared, at task completion. Uploading an `ro` resource is an error, not a no-op.

   The transports split by how often the data changes, because the cost of an update is what decides the storage shape. Stable artifacts take `object`/`prefix` — one write, one version, done. Frequently changing state takes `snapshot`: a restic-format repository (rustic reads and writes it, append-only, content-defined chunking and deduplication) where `sync` backs the path up into a NEW snapshot and `ensure` restores one, in place, touching only files that differ. That is what makes "upload on completion" affordable for a working tree that changes every task, and it is why a snapshot repository is not the rejected whole-filesystem capture: it is bounded by one declared path, and the second snapshot costs what changed.

   **No write needs an approval, and the reason is mechanical rather than optimistic.** Every transport allocates a version instead of overwriting one: git writes a commit on a branch, object storage keeps object versions, a snapshot repository is append-only. The REFERENCE to the current version is a control-plane record, not the node's choice, so a bad write is undone by not advancing a pointer — the previous state was never destroyed. `sync` therefore returns the reference it produced (branch and commit, object version, snapshot id and tags) so the result carries both the audit trail and the undo handle. A write that could only be judged safe in advance would need a human; a write that allocates a version needs a pointer.
8. **The node holds no durable credential. It asks for one, spends it itself, and the data path does not pass through the control plane.** Material — a presigned object URL, a short-lived VCS token — is minted by the control plane when the task asks for a resource, delivered over the connection, and spent by the node directly against the store: no relay, because a relay would make the control plane the bandwidth of every artifact. It lives in the node's memory for the length of one `ensure` or one `sync`, is never written to disk, never placed in the environment, and never handed to the guest. In the ordinary case its exposure window is empty, because `ensure` runs before the script starts and `sync` runs after it exits; a resource discovered mid-task is the exception, and there the guarantee is structural rather than declarative — the guest runs as a different uid, so a credential inside the node's process is not readable by the delivered code. The model never sees a credential at all: it asks for a resource by name and receives a path.
9. **The workspace is not a separate concept.** It is a resource of type `git` (say, `repo`), and `cwd` points into it. An environment is `image + network + task`; everything on disk is a resource. `fs_scope`, `deny_read` and `cwd`-as-a-policy have no meaning in the container class — the paths are ones we created and there is nothing else in there — and they survive only as the `Host` class's coarse grant.
10. **The node IS the container's root process, so container control stops existing.** `docker run --rm --init <image> effector --control-plane <url> --token <…>` — the node is PID 1, delivered scripts are its children, and when it exits the container exits. That deletes the container-control surface from the executor entirely: no create/attach/exec/destroy API inside the node, no orphan containers after a crash, no separate reaper, because the container's lifetime IS the process's lifetime. The privilege moves out of the executor and into the LAUNCHER — a `Job` in a cluster, a minimal spawner (or the control plane itself, or a systemd template unit) on a single machine — so the component that runs untrusted code is no longer the component that can create containers.
11. **One token at the dial; the connection is the authority.** The node authenticates once when it connects, and every dispatch afterwards rides that connection and carries no credential of its own. Two consequences, both simplifications: authorization cannot arrive from anywhere else, so there is no per-call check to write or to forget, and revocation needs no mechanism — closing the connection is the revocation. The Register frame stops being a proof of identity (the ed25519 signature, the nonce challenge, `read_signing_key`, `private_key_path`) and becomes a declaration of shape: alias, classes it can host, images it can run. The node's lifetime is one rule with two inputs — it exits when the connection ends, and it exits when its idle grace runs out, whichever comes first — so the grace timer is not a table in a pool manager but the process's own timeout. A token keeps working until it is replaced: it is a machine's key, and a fleet-wide expiry date only manufactures an outage on a day nobody chose. Revocation is re-minting — the registry stores the token's DIGEST, never the token, so a new credential makes the old one stop matching on the next dial — and one live connection is admitted at a time (a second connect replaces the first), so a leaked token cannot fan out into a second node and its window is a connection, not a lifetime.
12. **Approval exists, and it belongs to a skill STEP, never to a syscall.** The environment bounds what damage is possible; what remains is a decision only a person can make — deploy this, spend this, touch that system — and such a decision is meaningful only at a unit a person can actually read. That unit is the skill as k10r stores it (preconditions, steps, experience, post-verification), and the decision point is one step inside it, where the control plane can put a FORM in front of the reader: choices, parameters, the verification that will follow. A form asks for what the model cannot know; it does not ask permission to run `rm`. This is why the granularity is a step and not a call: a per-call prompt is answered by reflex, a step-level form is answered by reading. Effector takes no part: it has no approval surface and must not grow one, because the node sees calls, not skills — and a component that can pause a turn belongs to gravity, which already owns turn control.
13. **Effector keeps what Docker does not provide.** The node owns the control-plane connection, code delivery, the induction frame protocol (typed invoke/iterate streams, not a byte pipe), per-call accounting, cancellation semantics, the environment registry, its own idle lease, and resource provisioning. Docker supplies isolation, limits, an image, a kill handle and pipes — none of which are frames, delivery or accounting. The simplification is real but it is conceptual, and it is listed below.

## Considered and rejected

- **Keep the jail as the default and treat containers as an option.** That leaves two containment stories to keep honest, and the jail's story is the one whose enforcement had to be patched on 2026-11-09 to reach a proxy at all. One boundary, chosen explicitly.
- **Reuse containers by environment spec.** Cheapest cache, and it silently merges tasks — including across users. Rejected on the same ground that a shared memory surface had to be a per-user namespace.
- **Snapshot the container's filesystem to object storage on close.** A whole-filesystem capture is large and it uploads on every close, which turns the cheap part of the design into the slow part. The `snapshot` transport exists for a different job: one DECLARED path, appended to a deduplicating repository, so the second capture costs what changed. Persistence stays decided (`git` for text, declared `rw` resources for artifacts and state); what is not declared is disposable, and that is the point.
- **Gate writes behind an approval because they are destructive.** They are not: every transport allocates a version (branch, object version, append-only snapshot) and the pointer to the current version belongs to the control plane. The approval would protect nothing a pointer rollback does not already protect, and it would put a human's attention in the path of every task.
- **Let the model compose `git` and `s3` commands inside the container.** It cannot be done without putting the credentials in the container, which is the thing this design exists to prevent.
- **Drive containers by composing `docker` CLI invocations.** A CLI string has no owner: it can half-fail, it leaves containers behind, and the lifecycle of a resource needs an idempotent API. The Docker Engine API is used directly; the CLI stays a debugging tool for people.
- **Give the sandboxed script the Docker socket.** Equivalent to handing it the host.
- **Approval at the syscall or the single write.** It protects nothing the environment does not already bound, and it spends the one resource that cannot be scaled. What a person can actually judge is "should this step happen, with these parameters" — a skill step in k10r, with a form in the UI. Mixing the two levels means replacing design with dialogs.
- **Relay resource material through the control plane.** It would keep every container free of credentials, but it makes the control plane the bandwidth of every artifact (models, datasets, build output) — a cost that grows with the customers, not with the control plane's actual job. Minted material spent directly by the node keeps the property that matters (nothing durable in the container) without the relay.
- **Give the guest a long-lived storage credential.** The transfer is a node-side action; the guest's job is to write files into a path. A credential in the guest is authority in the one place that runs code nobody reviewed.

## Consequences

- **A node declares the classes it can host, and refuses the rest by name.** A machine without Docker is an in-process + host node; it does not silently accept a turn's fresh script and run it with no boundary. The refusal reuses the shape the mounts already use ("no environment here can host this class — this node declares: in-process, host"), so the deployment's actual capability is stated rather than assumed.
- **The LAUNCHER becomes the privileged component, and the node holds nothing durable.** Whoever creates the container holds the Docker socket (≈ root on the machine) — a `Job` in a cluster, a small spawner on a single host. The node, which runs the untrusted code, holds no socket, no identity key and no storage credential: one token at the dial, and per-transfer material that lives in memory and dies with the transfer. The old stance ("the container that runs untrusted code holds no data-plane credentials") is unchanged; it is now enforced by the shape instead of by discipline.
- **The node becomes a resource manager, and the control plane becomes the keeper of pointers.** `ensure`/`sync` per resource, one `snapshot` repository for state that changes every task, `object`/`prefix` for what does not, `git` for text. The node moves bytes and reports the reference it produced; the control plane records which reference is current, which is what makes a rollback a pointer move rather than a restore. This job was missing from the earlier architecture, not omitted on purpose.
- **The registration handshake shrinks, and the executor gains a job it should always have had.** The ed25519 register signature, the nonce challenge and `private_key_path` retire: identity is established by the token at connect, and the frame that follows only describes the node. What arrives in their place is a resource manager — `ensure`/`sync` with minted material — which the earlier architecture never specified because it never decided where durable data crosses the boundary.
- **Routing stops being a problem.** Today a call must reach "a registered node that serves this language", which is a scheduler in disguise. With one container per task, whoever creates the container has already decided where the task runs; the control plane dispatches instead of scheduling.
- **PID 1 is a duty, not a formality.** The node reaps its children, handles `SIGTERM`, and forwards it to the guest; `--init` (tini) covers the parts the node does not need to know about.
- **Images become deployment artifacts.** Their build, distribution, and offline availability replace the current runner scripts as the thing that can go wrong at a customer site. The language-axis drift table (a mount per alias × language) collapses into "the image is the mount", which is a simplification and also a policy change: a node no longer declares which languages it serves, it declares that it can pull and run an image.
- **The frame protocol survives, and that is not inertia.** A container gives a byte pipe; it does not give typed invoke, stream iteration, cancellation at a boundary, or per-row accounting. Removing the protocol would move all of that into shell scripts and JSON on the command line.
- **A task's calls share a container; tasks do not.** Intermediate files persist within a task and vanish with it. The visible cost is that a task cannot inherit another task's downloads, and the invisible benefit is that no approval is needed to make a mess.
- **Cost, measured rather than assumed:** ~0.2 s per container, once per task in the common case (the grace period absorbs a turn's later calls).
- **Open, deliberately not ruled here:** where the image is declared (task, skill, or node default); what a node does when an image cannot be pulled; whether `sync` failure fails the task (it must be visible, and this record does not choose between "task fails" and "task succeeds with a loud artifact error"); the write-lock rule for two tasks declaring the same `rw` resource name (a name is the identity of a logical resource, so one writer at a time is the current intent); and how the guest's uid is guaranteed on every backend — the credential-in-memory rule leans on it, and today it is a deployment assumption rather than something the node checks.
