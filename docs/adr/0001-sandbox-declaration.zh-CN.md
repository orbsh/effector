# 0001 — 围栏由节点自己声明，且每一条声明都指明它的执行点

> **语言：** [English](0001-sandbox-declaration.md)（主文档） · [中文](0001-sandbox-declaration.zh-CN.md)

**状态：** Accepted（2026-10-14）。随本记录落地：对 jail 能执行的部分，声明面补齐；
无法执行的声明在启动时被拒绝。仍开：出网允许清单所需的代理路径、seccomp 配置，
以及 `command_exec` 的执行机制（或把该字段退役）。
**日期：** 2026-10-14

## 背景

effector 是下发代码**唯一**的围栏层：代码在会话进程里跑，而 jail（bubblewrap，
由 `sandbox-runtime` 生成）就是那道边界——它下面没有按操作再套一层的容器。节点对
这道边界作出的承诺就是它的 `CapabilitySurface`，在注册帧里发布给控制面。

2026-10-14 的核对发现，声明与执行没对上：

- `fs_scope` 确实到了 jail，成为 `allow_write`——被执行了——但该字段自己的文档写着
  "下发脚本可读/写的路径"。**读**并不受它约束：凡 jail 没绑成只读的东西都读得到。
  声明比机制更宽。
- `deny_read`、`cwd`、`allowed_domains` 在 `SandboxPolicy` 里躺着，却没有任何声明喂它们
  ——`sandbox_policy_for` 把 `deny_read: []`、`cwd: temp_dir`、`allowed_domains: []` 写死。
  策略结构描述了一个没人能声明的面。
- `network`（`none` / `allow` / `open`）与 `command_exec` 被声明了、在注册时发布了，然后
  **没有任何代码消费它们**：出网允许清单本该骑 `sandbox-runtime` 的代理（从未配置），
  jail 直接拒绝出网；而 jail 内部能否 exec 没有任何策略字段拦或放。两条被发布出去的
  "能力"其实不是能力。

所以缺口不是"少一个声明面"，而是**声明没有执行点**——属于撒谎的那一类：控制面按节点
声称的内容去派活，而一份节点兑现不了的声明，会把活派到一台行为和它宣称的不一样的机器上。

## 裁决

**RULING——节点自己的声明是 jail 的唯一来源，兑现不了的声明是启动错误。**

1. **jail 的每一个字段都来自节点自己的 `CapabilitySurface`。** 策略里没有任何一项是从
   控制面的帧推导出来的，也不存在"有声明却仍写死"的字段：`deny_read` ← 声明的
   `deny_read`，`cwd` ← 声明的 `cwd`（不声明 = 声明面出现之前的默认值，系统临时目录），
   `allowed_domains` ← 声明的 `network`。一台机器的 jail，真相在它自己手里。
2. **`fs_scope` 是"写"的范围，并且它就这么写。** 它之外一律只读，而"读"由 `deny_read`
   管辖（凭证、shell 配置、别人的目录）。一个字段的文档比它的机制更宽，是有安全后果的
   文档缺陷，不是特性。
3. **没有执行点的声明在启动时被拒。** `EffectorConfig::validate()` 在节点拨号之前就跑
   （与"凭据环境变量缺失即启动失败"同一形状）：今天 `command_exec: true` 与任何非 `none`
   的 `network` 都是错误，因为没有任何东西接它们。报错要点名缺哪一段执行路径，好让运维
   知道该去建什么，而不只是知道某个值被拒了。
4. **兑现不了的东西要被点名，不许藏。** 一个字段只有在它的执行点存在之后才可以被声明；
   在那之前它不出现在声明面上（既不静默忽略，也不"接受但打条警告"），而那段缺口列在
   `docs/PLAN.md`（Phase 5 的沙箱条目）里，而不是留着让下一个人重新发现。

## 已考虑并否决

- **把围栏策略声明在控制面**（按 mount 写进 prism 清单）。那等于让控制面从外部指挥一台
  机器的 jail，而按 mount 的粒度还要把策略挂到每一次调用的线上。机器才是知道自己能暴露
  什么的那一方，也正是"声称的行为"所描述的那一方——犯错的主体和拥有的主体是同一个。
- **保留那些没有执行的声明，只加一条启动警告。** 发布出去的能力就是控制面用来派活的承诺；
  一条没人看的警告并不会改变这条承诺还在持续作出的事实。
- **把 `fs_scope` 也当成读范围**（读被限制在列出的路径内）。这会破坏最普通的情形——脚本
  要读 `/usr`、系统库、运行时的 `/etc`——却假装自己是最小权限。刻意选择的形状是"写受限、
  读开放"，读侧用 `deny_read` 声明。
- **按语言分别拦截**（python 审计钩子、steel 不发权限、nu 预解析过滤）。早前已否决，此处
  仍然：要的是一道进程边界，不是 N 道各漏各的语言半笼子。

## 后果

- `CapabilitySurface` 增加 `deny_read` 与 `cwd`；`fs_scope` 的文档改正为"写范围"。两个新字段
  默认为今天的行为，所以一个什么都不声明的既有节点，jail 与从前一致。
- `EffectorConfig::validate()` 由 `remote::run` 调用——那是唯一入口，于是二进制与所有进程内
  嵌入方（含 prism 的测试）拿到同一条拒绝。
- 测试：配置层的拒绝用例（`effector-config`）与"声明 → 策略"的映射用例
  （`effector-runtime::remote`），都是单元级、贴着它们钉的代码。
- `docs/USAGE.md` / `USAGE.zh-CN.md` 记录两个新字段与 fail-closed 规则。
- **仍开（列在 `docs/PLAN.md`）**：让 `NetworkPolicy::Allow` 能被执行所需的代理路径、seccomp
  配置、能执行 `command_exec` 授权的机制（或者把该字段退役）、以及读拒绝的更细形态
  （sandbox runtime 接受模式匹配，而这里的声明只传字符串）。
