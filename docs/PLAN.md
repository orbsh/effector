# PLAN

Design lives in the wiki (stateless-agent-architecture.md); this file only sequences phases.

RENAMED 2026-11-07: the live execution unit is `executor`. Every earlier entry here that spells `session` (or `resident session`) for it reads `executor`; `Sessions` / `ResidentSession` / `SharedSession` read `Executors` / `Executor` / `SharedExecutor`; `Trait` and the registry live in `carrier/executor.rs`; the wire field is `ToolCall.executor`.

**Iron rule — effector never depends on Aura crates.** All coupling with Aura is
limited to the frame protocol (serde types in `effector-protocol`). The effector is
upstream-agnostic: any service that speaks the frames can drive it — the
"Aura Booth" deployment form is implemented entirely on the Aura side
(connection plane adapts outbound WS frames to Realm mailbox semantics);
scheduling semantics the effector needs (same-node seriality, call timeout) are
its own mailbox + deadline, not Aura's `pending_calls` — that scan is
control-plane side. Hitching to another service = that service holds the WS
server; effector code is unchanged.

## Milestone A — Runtime

- [x] Phase 0 — Workspace skeleton: `crates/{runtime,protocol,config}`; task contract (tool_call in → tool_result out); capability surface definition (fs scope, command exec, network — what a skill may touch; no credentials). Isolation model: **the Effector itself runs as a container** (base image + on-demand dependency install, e.g. Python + libs) — isolation is per-node, not per-skill. Consequence stated openly: skills inside one container share its filesystem; the "restricted world" is enforced by the capability surface (app-layer checks), not by container boundaries. Acceptable under user-namespace isolation (isolation cuts by user, not by skill); revisit per-skill isolation only if multi-tenant shared nodes become real.
- [x] Phase 1 — Runtime carriers: steel / python (PyO3) / wasmtime (the Wasm engine; wasmer/wasmi were engine candidates, not languages; koto/rune predate the three-language ruling and are dropped) + nushell (subprocess, CGI-shaped: JSON via stdin, structured result via stdout — completes the language-selection quadrant grid), feature-gated; per-operation language declaration; script-only operations end-to-end. ROSTER CORRECTED 2026-11-09: the wasmtime carrier retired with aura PLAN 4.21 and nushell rides the INDUCTION carrier, not a carrier of this crate — the surviving roster is `steel` / `python` here plus `induction` and the `exec` runner (`crates/runtime/Cargo.toml:39-42`, `README.md:28`); two stale "wasmtime arm" comments remain at `crates/runtime/src/carrier/executor.rs:614` and `:648-650`.

## Milestone B — Effector

- [~] Phase 3 — Outbound registration: deploy on any machine and it operates that machine. Connection-direction/data-direction decoupling: on startup the effector actively connects to the control plane and registers (presence + capability list), keeps the connection open, tasks are pushed down the connection (WS frames) — no inbound ports, network ingress topology irrelevant; no degraded fallback (long-polling explicitly rejected — WS-only is the contract). Effector is an Aura Booth type (booth_type = Effector, partition_key = node_id): the control plane's calls are standard `ctx.invoke()` routing — registration credential = user credential, capability list (the carried languages) written into the user's namespace registry; target resolution = user namespace + node alias + operation (`effector:home-pc:read_file`), where the operation is a registered booth/script — the Effector ships no built-in operations, every operation is user-written or AI-generated code delivered through a carrier (nushell/python/steel/wasmtime). Same-node seriality free via Booth mailbox semantics; timeout/error reuse `pending_calls` deadline scan.

  - Domain allowlists LANDED 2026-11-09 — the field is consumed, not carried. The node starts the sandbox runtime's HTTP and SOCKS5 proxies with a `DomainFilter` built from the declared list (`crates/runtime/src/egress.rs`), bridges each to a UNIX socket with its own tokio task (the jail is a different network namespace, so loopback is not a path between them), and hands the jail two socket paths plus two fixed loopback ports through `SandboxPolicy::Bubblewrap.proxy`. Inside, `egress::jail_prelude` starts two `socat` bridges and exports `http_proxy`/`https_proxy`/`ALL_PROXY`; the spellings are load-bearing and all three were found by running it: `set -m` (a POSIX shell sends a background job's stdin to `/dev/null`, which a userns jail cannot open), the bridges write to STDERR (stdout is the protocol channel), and the shell does NOT `exec` the script (an exec drops the cleanup that kills the bridges). `validate` now accepts `allow [...]` with `sandbox: true` and refuses `open` (an unshared namespace cannot be unrestricted), an empty list (the filter reads it as allow-all), and `allow` with `sandbox: false` (no jail, no bridges). Gates: `crates/runtime/tests/egress.rs` 3/3 against a REAL bwrap jail — an allowed host answers through the proxy, the same script with a list that omits it does not, the generated command carries both sockets and the bridges, and the sockets live outside `/tmp` and `/run` (the jail tmpfs-es both).

Also unowned and NOT fixed: the generator's mandatory deny discovery binds `~/.bashrc`-style files read-only, and on a nix home those are symlinks, so bwrap refuses `--ro-bind` onto a symlink destination and every sandboxed call fails. `fs_scope` growth does not help; this needs a decision about who owns the deny list.

Original text: A skill is emergent in the Krystallizer graph; Gravity drives the LLM — the LLM selects the operation and generates its arguments, and that selection is the skill's execution. What the Effector receives is an operation, its declared language, its code, and its arguments. Two payload forms declared in the task context: `inline` (bytes in the frame — py/steel, KB-scale) and `link` (URL + content-hash version + expected hash — Wasm, MB-scale; optional control-plane HTTP port, CDN-cacheable by version, hash verifies bytes). - [x] Phase 4.5 — Host-side storage service (ADR-0010): **WITHDRAWN (2026-09-20)**.
  - Landed, then removed in full: `kv_executor.rs` (NestStorage receiver role), the `Frame::Kv` / `KvFrame` / `Frame::KvRefused` wire frames, `KvExecutorDecl` + `EffectorConfig.kv_executors` (`name` / `ns` / `data_dir`), the `KvRegistry` dispatch arm, both KV test files, and the effector's `okm-core` / `okm-wire` dependencies — the effector now has no okm coupling of any kind.
  - Structural reason: **the effector holds no storage.** Data has no reason to live on an execution node — hosting it adds a directory to place, size and back up, plus an engine lifecycle, while every operation the node runs is delivered per call and holds nothing between calls. The key prefix is not an execution-node concept either: it is what the CONTROL PLANE derives from the sender's identity and business logic (Gravity's data = its own ns, then the partition id, then the event id, resolved by lookup), so a declared prefix on a dumb receiver could only restate a decision taken elsewhere — and a `ns`-shaped field carried okm's vocabulary into a component whose contract is bytes only.
  - Consistent with okm ADR-0010, which places the receiver on Aura ("Aura's remote-storage receiver", "Krystallizer hosting on Aura"): the effector's executor was a second placement of the same role, not a fifth backend shape.
  - **Where the persistence requirement is served instead — the founding path, not a fallback**: a delivered script's durable state goes through the ctx bridge (`ctx_state_get` / `ctx_state_set` / `ctx_state_delete` / `ctx_invoke` ride `Frame::Host` to the control plane, which executes them against its own store). This is the project's opening stance ("持久化与恢复全部沉到记忆系统"; stateless = the executor holds no session state, state lives in Krystallizer), so persisting from a script is the initial requirement and the effector holding nothing between calls is what serves it — never describe it as a someday case.
  - **And the effector must not hold the data plane's credentials**: the node runs untrusted code in a container, so it is not given storage credentials ("容器（执行不受信任代码）不持有数据面凭证"). Hosting an engine there contradicts that stance, not merely adds an operations burden — this is the hardest of the reasons.
  - Anti-pattern recorded so it is not re-proposed: an operation that genuinely needs local temporary data creates its own SQLite file via python/nushell. That is an operation's private business, never a effector-side storage surface.

Whether an operation is AI-generated-live or pre-audited is control-plane policy (Gravity/Krystallizer), not a Effector concern. This is the ONLY containment layer (no per-operation container boundary beneath it) — the check must be enforced at execution, not just at dispatch-declaration. - [ ] Phase 6 — Data-path discipline: control plane carries instructions and result summaries only — Result stays message-sized; large artifacts (files, binaries) are handled by the operation on the Effector side (local fs, user-configured transfer tooling, transport operations). Transport-reachability requirements (direct connection / same VPN) ride skill metadata on the Gravity side — the control plane neither knows nor governs the data path. AI-generated invoke arguments are instruction semantics (paths, options, fragments) and naturally bounded; a loose inbound message cap on the control plane guards anomalies only, it is not a data-plane design.

## Open items, measured 2026-11-09 (none of them a phase)

- **The jail covers the process carriers only — RULED 2026-11-09**, written into ADR-0001 point 5 (both languages): `fs_scope`/`deny_read`/`cwd` bind `exec` and `induction`, while `steel` and `python` run inside the node (`crates/runtime/src/carrier/executor.rs:618-624`, and `steel` is a DEFAULT feature, `crates/runtime/Cargo.toml:39`). What that leaves open is only the fail-closed half: a `sandbox: true` registration must not be published by a node whose carrier cannot enter the jail at all.
- **`sandbox: true` with no `bwrap` on PATH registers and serves, failing per call.** `crates/config/src/lib.rs:104-105` documents the requirement; `crates/runtime/src/remote.rs:507-519` validates declarations and dials without probing PATH; the absence only surfaces at spawn (`crates/runtime/src/carrier/exec.rs:1116-1135`). A node that cannot jail must not publish a capability list — the check belongs beside the existing fail-closed gate.
- **A stop reaches a node and the node says whether it could act — LANDED 2026-11-09.** `Frame::Interrupt { call_id }` in, `Frame::Interrupted { call_id, landed }` out; per-call `CallControl` (a flag the blocking wait re-reads every 50 ms, plus a hook the carrier arms when it can reach the work). The induction carrier arms it by writing induction's `interrupt` frame for the frame id it minted, so the guest's handler learns while its caller stops waiting either way. `landed: false` is the honest answer from a carrier with no way in (steel and python are in-process VMs pinned to one thread, `arm_interrupt` defaults to arming nothing) and the control plane must not read it as "it stopped". Every carrier that can act now does, and the ones that cannot say so. The one-shot `exec` carrier kills the child (the kill IS its stop: a script mid-run has no channel to be told anything); the `induction` carrier writes the interrupt frame so the guest's handler learns, and the shared/unbounded seam carries the handle per call — on the carrier it would belong to whichever call armed last. `steel` and `python` arm nothing by design (in-process VMs pinned to one thread) and answer `landed: false`. Gate: `exec_carrier::an_interrupt_releases_the_wait_and_reaches_the_guest` (real guest from the induction shim, 30 s handler ceiling, released in ~150 ms).
- **`command_exec` RETIRED 2026-11-09.** Decided retire, not wire, and the reason is structural rather than budgetary: a node exists to run a delivered script inside a jail that admits `exec` by construction, so "may execute" is not a capability distinct from existing and no policy field could ever carry it. Field, `false` default, refusal arm and its test are gone (ADR-0001's Update); a config that still names it fails at parse time on an unknown field.
